如何填写 REVIEW.md

它是写给 reviewer 的评审口径，不是给人读的说明文档。写“什么算坏”，不写“什么是好”。

1它什么时候被用到

diff 触及某模块src/content/ 下有改动
→
只加载那一份src/content/REVIEW.md，其余不加载

改根目录 REVIEW.md 时按平台口径审它自己；空着也不报错，但正文会标注“口径未填写”，reviewer 退回通用三闸门。

2四个小节，各填什么

小节（名字别改）填什么反例 → 正例
## What failure looks like here 这个模块“坏了”具体长什么样。一条一句，必须能验收。 注意边界情况 → 划词后文字没进输入框
## Paths to skip 哪些东西看起来可疑、其实是正常的。这条直接决定误报率。 随便一点 → vendor 副本、有意的静默 catch
## Evidence format 这个模块的改动必须附什么证据：命令、截图、在哪个站点操作。 要有证据 → 附改动前后 console 输出
## Nit budget 这一份最多报几条，超出只报最严重的。 尽量少 → 至多 3 条

3一份填好的样子

# REVIEW.md — content scripts

Covers: `src/content/chat-bridge.js`, `src/content/page-tools.js`,
`src/content/pdf-main.js`

## What failure looks like here
- 侧边栏收不到页面选区:page-tools 拿到了选区却没 postMessage,
  或 chat-bridge 的 origin 校验把消息丢掉。
- 重复注入:同一次页面加载里内容脚本被注入两次,浮动按钮出现两个。
- PDF 选区错位:pdf-main 用了旧的 scrollTop,浮动输入框不跟随滚动。
- 任何把页面正文、选区写进 chrome.storage 的改动。

## Paths to skip
- `src/vendor/pdfjs/` 下的任何文件:上游整包,不在这里审。
- 有意的 `chrome.runtime.lastError` 静默分支:消息对端已关闭时是预期情况。

## Evidence format
- 必须说明:在哪个站点、哪一步操作下能复现。
- 涉及 DOM 选择的改动,附改动前后的 console 输出或截图。
- 不需要附 npm test 的输出(CI 会跑)。

## Nit budget
- 至多 3 条;超过的话只报最严重的那些。

4四条纪律

  1. 只有你能写。 reviewer 只读不改 —— 自己定义“怎么审自己”等于把判断权交出去。
  2. 控制在 60 行内。 超了说明在写散文，不是口径。AGENTS.md 已经因为太长被记了一笔。
  3. 不抄 AGENTS.md。 那里是项目通用规则；这里只写这个模块特有的东西。
  4. 改口径本身要停下。 改 REVIEW.md 会被分类器判成“中风险 + 必须人工”，因为它在改以后怎么审。

5写之前问自己三句

Q1

这条能不能判某个具体行为“坏了”？判不了就别写。

Q2

删掉它，reviewer 会误报什么？答不出来，说明它没用。

Q3

这些文件路径/行为描述，三个月后还成立吗？会变的写成原则，不写死行号。

顺序建议

先写 Paths to skip —— 它最直接地降低噪音，也最容易验证效果。
