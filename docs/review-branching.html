为什么旧 PR 会跑到旧评审脚本

一次真实事故的时间线复盘 —— 里面用到的 commit 都是这条仓库里真实存在的。

1事故现场

PR #5 推了新 commit，评审却输出了下面这段裸 JSON，并把计数写成 Critical 0：

那轮日志里的两行

reviewer script restored from base (ea99cd25e880a2077d1a62586248123764023573)
BASE_SHA: ea99cd25e880a2077d1a62586248123764023573

脚本是从 ea99cd2 取的。而 main 早就前进到 a3152f7 了 —— 那里才有 JSON 解析的修复。

2时间线：base.sha 停在了开 PR 的那一刻

main PR 分支 旧行为取脚本的位置 修复后取脚本的位置

关键点

pull_request.base.sha 是「这个 PR 的 base 分支在事件发生那一刻的 commit」， 但它在 PR 存续期间不会跟着 main 前移。PR #5 是 10:19 开的，之后 main 又合了 PR #6， 它的 base.sha 仍然是 ea99cd2。

于是「从 base 恢复评审脚本」这一步，恢复的是一个没有解析修复的版本。 评审结果又退回到把模型原始 JSON 贴进正文、计数写成 0 的样子。

3修法：脚本跟 main 走，diff 基准不动

取最新的是脚本，不是基准

git fetch origin "+refs/heads/$BASE_REF:refs/remotes/origin/$BASE_REF"
git show "refs/remotes/origin/$BASE_REF:.github/scripts/review.mjs" > .github/scripts/review.mjs

# diff 基准仍然是 PR 自己的 base，旧 PR 不需要 rebase
BASE_SHA: ${{ github.event.pull_request.base.sha }}

只换脚本来源，不动 diff 基准 —— main 上修了脚本，存量 PR 不用同步 main 也能用上； 而「这次 PR 相对它自己的 base 改了什么」保持原样。

4一个绕不过去的死循环：改脚本的 PR 无法自证

为什么不能干脆「跑 PR 里的脚本」？因为那等于让 PR 作者执行任意代码，而这一步持有 DEEPSEEK_API_KEY 和可写评论的 token。所以脚本必须来自 base。

推论

PR #6 改的是 review.mjs。它在自己身上被评审时，用的仍是 main 上的旧脚本。 你在那个 PR 里怎么同步 main 都没用 —— 脚本不是从 PR 分支取的。

唯一出路：先合并，再用一个普通 PR 验证。 PR #6 合进 main 之后，PR #8 用修好的脚本跑通了一次， 那一轮才第一次看到正常的 Findings: Critical 1 …。

但 yml 不一样

workflow 文件本身来自 PR 的 ref。所以改 review.yml 的 PR，跑的是它自己那份 yml。 对这类 PR 来说，「同步 main」是有意义的（避免和 main 上的 yml 结构冲突）， 而改 review.mjs 的 PR 里，同步 main 没有意义。

5什么时候会跑什么

事件ci.yml（语法 / 测试 / 打包）review.yml（评审）
向 PR 分支 push跑跑
开 PR / 重开 / 标 ready跑跑
合并进 main（push 到 main）跑不跑
直接 push main跑不跑

所以「PR 有自己的 CI」和「合并时也有 CI」是两条独立的运行：前者在 PR 分支上，后者在 main 上。

6这次事故真正教给我们的一件事

评审脚本的版本，不该由「PR 是在什么时候开的」决定，而该由「main 现在是什么」决定。 否则一个 PR 的价值取决于它开得早还是晚 —— 早开的 PR 会一直用旧规则被审。

代价是：脚本更新的效果对存量 PR 立刻生效，这一点需要知道（一次修复会影响所有在途 PR 的下一轮）。
