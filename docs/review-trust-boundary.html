可信程序 × 不可信输入

漏洞通常不来自“代码不可信”，而来自可信代码不安全地处理了不可信数据。

一条等式 可信程序 + 不可信输入 + 没有边界 = 漏洞

1边界划在哪里

不可信 · 来自 PR

PR 提交的代码 diff 文本 文件路径 / 文件名 artifact 内容
  • 能执行、能造文件、能写任意字节
  • 也能源源不断地做“提示词注入”
信任边界

可信 · 来自 main

workflow 定义 review.mjs API key
  • 程序可信，不代表它能安全处理上面那些输入
  • 边界必须在执行之前，不是执行之后

跨界只允许一种形式：数据。不允许“代码”，也不允许“路径指令”。

2三道锁，各锁一件事

1
锁 workflow 的来源 pull_request_target
PR 改不了要跑哪些步骤。
2
锁 checkout 的来源 ref: main
跑的是 main 上的脚本，不是 PR 的。
3
锁 secret 的邻居 job 隔离
key 与 PR 代码永不同容器。

3两个 job，一条单向的数据流

Job A · PR 处理

无 secret contents: read
  • 安装依赖、执行 PR 测试（不可信代码在这一格）
  • 生成 diff，写进 artifact
artifact · 只当数据传，名字固定

Job B · AI Review

持有 API key
  • checkout main，跑可信的 review.mjs
  • 读 Job A 传来的 diff，调用模型
  • 不 checkout PR 代码，不按 diff 里的路径读文件

4跨界之后，剩下的全是“输入”

zip-slip条目名带 ../，解压写穿目录
符号链接PR 放一个指向 /etc/passwd 的链接
路径拼接拿 diff 里的路径直接 join
体积炸弹超长 diff 拖垮 runner 与 token
提示词注入diff 里写“忽略以上规则”

对应做法：解压后校验仍在目标目录内 · 拒绝绝对路径与 .. · 先截断 · diff 永远只是数据

5五个问题，全答“是”才算过

问题安全答案
PR 能改到要跑的 workflow 吗？不能
持有 key 的 job 里 checkout 过 PR 代码吗？没有
有按 diff 里的路径去读文件吗？不读
artifact 名字是固定的吗？是
跑 PR 代码的那个 job 权限只读吗？是
